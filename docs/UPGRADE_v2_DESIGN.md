# Digest Pipeline v2 — 재설계 문서

> 작성 2026-07-20 · 대상: 단일 사용자(개인) 전용 지식 큐레이션 + 축적 시스템
> 선행 문서: `PROGRESS.md`(v1 개발 기록) · 이 문서가 이후의 기준 문서가 됩니다.

---

## 0. 한 문단 요약

v1은 "DS 콘텐츠를 매일 3건 요약해서 보내주는 파이프라인"이었고, 코드는 성숙했지만 **산출물은 실패했습니다**. 태그의 89%가 무의미하게 `MLOps`로 찍혔고, 점수는 8점에 뭉쳤고, 피드백이 다음 큐레이션에 영향을 줄 코드 경로가 아예 없었으며, 유튜브 자막이 차단돼 제목만 보고 퀴즈를 만들었습니다. **v2의 1순위는 소스 확장이 아니라 분석 레이어 재설계입니다.** 소스를 5개에서 58개로 늘리면 고장난 필터가 걸러야 할 양이 10배가 될 뿐입니다. v2는 (a) 프롬프트 지시 대신 **코드 게이트**로 품질을 강제하고, (b) 산출물을 HTML이 아니라 **구조화 레코드**로 저장해 축적 가능하게 만들고, (c) 피드백을 URL이 아니라 **개념**에 귀속시켜 루프를 닫고, (d) 축적된 개념 그래프를 **필터의 입력이자 아이디어 생성기**로 되먹입니다.

## 1. 진단 — v1은 왜 실패했는가

### 1.1 프롬프트로 고치려던 것이 전부 실패했습니다

이것이 가장 중요한 교훈입니다. `PROGRESS.md`에 "✅ 완료"로 적힌 항목들을 **실제 산출물로 검증하면 완료되지 않았습니다.**

아래는 **98일 / 247 아이템 전수 집계**입니다.

| 조치 (프롬프트 수정) | 의도 | 실측 결과 (n=247) |
|---|---|---|
| 1-10 점수 기준 정의 + "7~8이 과반이면 안 된다" | 점수 분산 | **점수가 7·8·9 세 값만 존재.** 표준편차 0.72, 6점 이하 0건 |
| "제목을 반복하지 말 것" + good/bad 예시 | 요약 품질 | 표본 20건 중 **4~5건(20~25%)이 제목의 번역·재진술** |
| "구체적 기술명·지표 필수, 일반론 금지" | 적용 아이디어 | **247건 전부 정확히 2개** — 내용과 무관하게 스키마를 채움 |
| 태그 taxonomy 인지 (F항목) | 태그 일관성 | `MLOps`가 **219/247 = 88.7%**에 부착 |

특히 마지막 두 줄이 결정적입니다. **적용 아이디어 2개와 퀴즈 2개가 247건 전부에서 고정**입니다. 콘텐츠가 얕든 깊든 형식은 항상 채워지므로, **품질 저하가 산출물 형태로는 전혀 드러나지 않습니다.** 4개월간 문제를 몰랐던 이유가 이것입니다.

그리고 태그 문제의 성격도 초판 진단과 다릅니다. **표기 흔들림(`ml-ops`, `ML 운영` 등)은 사실상 없습니다** — 593종 중 정규화로 병합되는 건 1.9%뿐입니다. 진짜 문제는 양극단입니다: `MLOps`는 88.7%라 변별력이 0이고, 나머지 592종은 대부분 1회성이라 역시 분류축이 못 됩니다. **즉 태그 정규화(F항목)를 아무리 해도 해결되지 않습니다.** 3.5절의 닫힌 패싯 도입이 필요한 이유입니다.

특히 태그는 원인이 명확합니다. 프롬프트가 `preferred_topics`(기본값에 `MLOps` 포함)를 주입하니 LLM이 이를 **"분류 기준"이 아니라 "붙여야 할 라벨"로 오독**합니다. 그래서 DB 마이그레이션 글에도, C++ `std::bit_cast` 글에도, 협업 멘토링 영상에도 `MLOps`가 붙었습니다. 검색·필터의 기반이 될 메타데이터가 신뢰 불가 상태입니다.

**→ v2 원칙 1: 품질 요구사항은 프롬프트 지시가 아니라 코드 게이트로 강제한다.** 검증 가능한 것은 검증하고, 위반하면 재시도하거나 탈락시킨다.

### 1.2 근거 없이 생성을 강제했습니다

모든 아이템이 예외 없이 "핵심 3개 + 아이디어 2개 + 퀴즈 2문항"입니다. 콘텐츠가 얕든 깊든 동일 분량이 강제되니 **패딩이 발생**합니다. 3/25 아카이브의 퀴즈 해설은 스스로 자백합니다 — *"**제목에 명시된** 핵심 주제는…"*, *"**제목에 '오픈형 멘토링'이라고 명시**되어 있어"*.

근본 원인은 GitHub Actions의 datacenter IP가 YouTube에 차단돼 transcript를 못 가져오는 것입니다. 유튜브가 전체 URL의 절반 이상인데 그 절반이 **본문 없이 분석**됩니다.

**→ v2 원칙 2: 근거(evidence)가 없으면 생성하지 않는다.** transcript 없으면 퀴즈 생성 금지, 깊이 점수 상한 강제.

### 1.3 피드백 루프가 코드상 존재하지 않습니다

👍/👎는 `liked_item_ids`에 저장됩니다. 그런데 `ANALYSIS_PROMPT`는 `topics`와 `keywords`만 주입합니다. **좋아요가 다음 날 큐레이션에 영향을 줄 경로가 없습니다.** `PROGRESS.md` A항목이 "반영되는지 불명확"이라 적었지만, 불명확한 게 아니라 없습니다.

게다가 URL 단위 저장은 학습 신호로 거의 쓸 수 없습니다. *어떤 개념*을 좋아했는지가 아니라 *어떤 URL*을 좋아했는지만 남기 때문입니다.

**→ v2 원칙 3: 피드백은 아이템이 아니라 개념에 귀속시킨다.**

### 1.4 산출물이 HTML이라 축적되지 않습니다

파이프라인 마지막 단계에서 구조를 버리고 HTML을 씁니다. 그 결과:

- 아카이브 검색·필터 불가 (`claude_code_archive_viewer.md`가 요구한 JSON 저장은 미구현)
- 같은 날 재실행 시 **이전 산출물 영구 소실** — 실제로 3/30에 3번 덮어써져 아이템 6건이 git 히스토리에만 남았습니다
- 시계열 분석 불가 (수집 후보 수, 스킵 사유, 사용 모델 등 메타데이터가 전혀 기록되지 않음)
- **Phase 2의 KG 구축 입력이 없음**

**→ v2 원칙 4: 구조화 레코드가 source of truth이고, HTML/Telegram은 그 렌더링일 뿐이다.**

### 1.5 소스가 고갈되어 30일마다 같은 콘텐츠가 재유입됩니다

> 이 절은 **98일 / 247 아이템 전수 분석**으로 재작성되었습니다. 초판은 로컬 작업트리(원격보다 99커밋 뒤처짐)의 2개 파일만 보고 작성되어 오류가 있었습니다.

소스 도달 현황은 **초판의 진단과 반대**입니다. HackerNews는 죽어 있지 않고 **63건으로 전체 1위 소스(25.5%)**이며, arXiv도 4건 있습니다. 도달하지 못한 건 The Batch·Data Elixir 둘뿐입니다.

| 소스 | 건수 | 비율 |
|---|---|---|
| HackerNews | 63 | 25.5% |
| NAVER D2 (+D2 Blog) | 76 | 30.8% |
| kakao tech | 43 | 17.4% |
| 데보션테크 | 30 | 12.1% |
| 토스 | 21 | 8.5% |
| 당근·우형·무신사 | 14 | 5.7% |

진짜 문제는 다른 데 있습니다. **고유 소스명이 9개뿐이고, 그 결과 소스 풀이 고갈되어 옛 콘텐츠가 재활용되고 있습니다.**

- **중복 재유입이 전체의 19.8%** (247건 중 49건, 고유 URL은 198개뿐)
- **재등장 간격이 정확히 30~37일** — 49건 전부. 30일 미만은 0건
- 원인은 `cleanup_seen_urls(days=30)`. **31일째 되는 날 seen_urls에서 삭제되어 같은 영상이 다시 들어옵니다**
- 중복 35건 중 31건이 YouTube — 채널이 5개뿐이라 새 영상이 동나면 옛 영상이 재등장
- 마지막 중복 발생 2026-07-16, **현재 진행형**

그리고 고갈은 처리량 붕괴로도 나타납니다.

| 월 | 일평균 아이템 | 평균 관련도 |
|---|---|---|
| 2026-04 | 2.58 | 8.24 |
| 2026-05 | 2.68 | 8.01 |
| 2026-06 | 2.79 | 8.15 |
| **2026-07** | **1.53** | **7.70** |

**→ 따라서 소스 확장은 "나중"이 아니라 긴급합니다.** 초판은 "분석 레이어를 먼저 고치고 소스는 나중에"라고 했는데, 전수 데이터는 **파이프라인이 이미 굶고 있다**는 걸 보여줍니다. 다만 순서 자체는 유지합니다 — 게이트 없이 채널만 늘리면 88.7% MLOps 태그가 그대로 58채널로 확산될 뿐이므로, **평가 하니스(Sprint 1) → 게이트 → 소스 확장** 순서는 그대로 두되 **간격을 최대한 좁힙니다.**

**→ 그리고 소스별 통과율·최종 등장일을 상시 계측합니다.** 30일 이상 미등장 소스가 이미 2개 있습니다(우형 blog 59일, 당근 38일).

## 2. v2가 새로 얻는 제약과 자유

### 2.1 "나 한정"은 제약이 아니라 해금입니다

단일 사용자로 목적을 좁히면 두 가지가 풀립니다.

**(a) 주거 IP를 쓸 수 있게 됩니다 → 유튜브 자막 차단이 해결됩니다.** v1 최대 병목은 GitHub Actions IP 차단이었고, 쿠키로도 우회 실패했습니다(`PROGRESS.md` 7항). 실측 결과 **YouTube 116건 중 타임스탬프가 채워진 건 1건(0.9%)** — 4개월 내내 자막 없이 제목·설명만으로 처리되고 있었습니다.

병목의 축은 **토큰 검증이 아니라 IP 평판**입니다. PO Token(YouTube의 봇 검증 토큰) 프로바이더를 붙여도 풀리지 않습니다 — bgutil 메인테이너들이 이슈에서 명시했습니다: *"youtube appears to have flipped some feature flag on their end breaking this solution for **most datacenter IP addresses**"*, *"Your IP has been blocked by youtube. This tool does **NOT** guarantee bypassing that."* 신고자는 **GitHub Actions에서 PO Token을 정상 발급받고도** 차단당했습니다.

**따라서 VPS도 답이 아닙니다** — datacenter IP라 동일하게 막힙니다. 주거 IP에서의 실측은 PO Token 없이도 4/4 성공했습니다.

**채택 방식: Tailscale exit node.**

```
VPS ──(Tailscale)──> 집 기기(PC 또는 라즈베리파이) ──> YouTube
      요청은 VPS 코드가 보내되, 나가는 IP는 주거 IP
```

큐 동기화·write-back 로직이 필요 없어집니다. VPS 코드는 그대로 두고 네트워크 경로만 바뀝니다. 설정 15분, 무료.

> **집 기기는 무엇이든 됩니다.** 지금 쓰는 PC가 이미 조건을 충족합니다(집 와이파이에 연결돼 있으므로). 라즈베리파이는 "PC 켜는 걸 신경 쓰기 싫을 때"의 선택지이지 필수가 아닙니다. 핸드폰도 IP 조건은 맞지만 절전·배터리 최적화로 백그라운드가 죽어 실용성이 없습니다.
>
> 집 기기가 꺼져 있는 동안은 3.3절 **H축(반감기) 기반 대기 정책**으로 흡수합니다 — `ephemeral`은 자막 없이 즉시 발송, `foundational`은 최대 7일 대기.

> 참고: `yt-dlp-get-pot` 플러그인은 2025-11 아카이브됐습니다(프레임워크가 yt-dlp 코어에 내장). 오래된 블로그의 플러그인 설치 안내는 무효입니다. 진단법 — 로그에 `[youtube] [pot] PO Token Providers: ...`가 정상인데도 차단되면 **IP 문제이므로 프로바이더를 바꿔도 소용없습니다.**

**(b) 멀티유저 설계를 버릴 수 있습니다.** `PROGRESS.md` I항목(멀티 유저)은 **폐기**합니다. `user_id="default"` 하드코딩을 유지하고, 그 대가로 프로필을 훨씬 무겁고 풍부하게 만들 수 있습니다 — 개념별 선호 벡터, 학습 이력, 망각 스케줄 등.

### 2.2 대신 새로 생기는 제약: 볼륨

소스를 58채널로 늘리면 하루 후보가 **40~60편(유튜브) + 20~30건(RSS/arXiv/HN)** 수준이 됩니다. 현재 `MAX_ITEMS_PER_DIGEST=3`이므로 **97~99%를 버리는 필터**가 필요합니다. v1의 절대 채점 스코어러로는 불가능합니다. → 5장의 퍼널 설계로 대응합니다.

## 3. 루브릭 v2 — 단일 점수를 버립니다

### 3.1 왜 `relevance_score` 하나로는 안 되는가

"DS 현업 관련도 1-10"은 주제를 CS·사업·트렌드로 넓히는 순간 무의미해집니다. 노정석 인터뷰의 DS 관련도는 3점이지만 사용자에게는 최상급 가치일 수 있습니다. 축을 분해해야 합니다.

### 3.2 5축 루브릭

각 축은 **독립적으로 채점되고, 용도에 따라 다르게 가중**됩니다.

| 축 | 질문 | 0점 | 10점 | 채점 주체 |
|---|---|---|---|---|
| **N** Novelty | 내가 이미 아는 것인가? | 기존 개념만 재진술 | 그래프에 없는 개념 다수 | **코드**(KG 조회) |
| **A** Actionability | 읽고 나면 뭘 할 수 있게 되는가? | 인식만 바뀜 | 구체적 기법·도구·수치를 바로 적용 가능 | LLM + 게이트 |
| **D** Depth | 정보 밀도가 있는가? | 제목의 재진술 | 메커니즘·트레이드오프·실패사례 포함 | LLM + **근거 게이트** |
| **H** Half-life | 얼마나 오래 유효한가? | 오늘 뉴스 | 원리·수학·아키텍처 원칙 | LLM (분류형) |
| **F** Fit | 내 관심 궤적에 맞는가? | 무관 | 최근 관심 개념과 인접 | **코드**(선호 벡터) |

**N과 F를 코드가 채점하는 것이 핵심입니다.** LLM에게 "이게 사용자에게 새로운가?"를 물으면 알 수 없으므로 환각합니다. 하지만 **추출된 개념이 KG에 이미 있는지는 조회하면 압니다.** v1의 개인화 실패는 개인화를 LLM에게 맡겼기 때문입니다.

```
N = 1 - (기존_개념_수 / 전체_추출_개념_수)          # 코드 계산
F = cosine(개념_임베딩_평균, 최근_90일_선호_벡터)      # 코드 계산
```

### 3.3 근거 게이트 (Depth의 하드 상한)

프롬프트 지시가 아니라 **코드에서 강제**합니다.

| 확보한 근거 | Depth 상한 | 퀴즈 | 적용 아이디어 |
|---|---|---|---|
| 전체 transcript / 본문 | 10 | 허용 | 허용 |
| 부분 transcript / 초록 | 6 | 허용 | 허용 |
| 설명글(description)만 | **3** | **금지** | **금지** |
| 제목만 | **1** | **금지** | **금지** |

`ContentAnalysis`에 `evidence_level` 필드를 추가하고, 파이프라인이 이를 **수집 단계에서 결정**해 분석 결과를 검증합니다. LLM이 상한을 넘는 점수를 반환하면 clamp하고 로그를 남깁니다. 퀴즈·아이디어는 애초에 프롬프트에서 요청하지 않습니다.

> 이 게이트 하나로 v1 산출물 문제의 절반이 사라집니다. "제목에 명시된 대로…"라는 퀴즈 해설은 구조적으로 생성 불가능해집니다.

### 3.4 절대 채점을 버리고 상대 랭킹으로

v1은 아이템마다 독립 채점해서 8점에 뭉쳤습니다. v2는 **후보군을 한 번에 넘겨 순위를 매깁니다**. 분산이 구조적으로 강제되고, 토큰 증가는 5장의 퍼널(2단계에서 메타데이터만 사용)로 상쇄됩니다.

```
Stage 1 입력: 후보 60건 × (제목 + 소스 + 설명 200자) ≈ 15k 토큰
출력: 상위 15건의 ID + 사유 한 줄
```

### 3.5 태그 — 2계층으로 분리

v1 태그 붕괴의 해법입니다.

**Layer 1: 닫힌 패싯 (LLM이 선택만, 코드가 검증)**

```python
DOMAIN     = ["ai-ml", "data-eng", "software-eng", "systems", "product",
              "business", "research-method", "career", "tools"]   # 택 1~2
CONTENT_TYPE = ["paper", "case-study", "tutorial", "talk", "news",
                "interview", "opinion", "release"]                # 택 1
HALF_LIFE  = ["ephemeral", "seasonal", "durable", "foundational"] # 택 1
```

목록에 없는 값을 반환하면 **거부하고 1회 재시도, 재실패 시 `unknown`**. 자유 생성이 불가능하므로 `MLOps` 앵커링이 원천 차단됩니다.

**Layer 2: 개념 (KG에서 해소)**

자유 추출하되 기존 그래프의 개념과 **엔티티 해소(entity resolution)**를 거칩니다. `MLOps` / `ml-ops` / `ML 운영`이 같은 노드로 병합됩니다. 신규 개념만 노드로 추가됩니다. 이 과정이 곧 N축(Novelty) 계산입니다.

**그리고 `preferred_topics`를 프롬프트에서 제거합니다.** 개인화는 F축(코드 계산)이 담당하므로 프롬프트에 관심사를 넣을 이유가 없어졌습니다.

### 3.6 시스템 자체를 채점하는 메타 루브릭

주간으로 자동 산출해 대시보드에 남깁니다. **이 지표가 나빠지면 프롬프트가 아니라 게이트를 고칩니다.**

| 지표 | 정의 | 경보 임계 |
|---|---|---|
| 태그 엔트로피 | Layer 1 패싯 분포의 섀넌 엔트로피 | 특정 값 점유율 > 40% |
| 점수 분산 | 최종 순위 점수의 IQR | IQR < 1.5 |
| 소스 도달률 | 소스별 (발송 / 수집) 비율 | 30일간 0인 소스 존재 |
| 근거 확보율 | evidence_level ≥ 부분 인 비율 | < 70% |
| 개념 신규율 | 신규 노드 / 전체 추출 개념 | < 10% (정체) 또는 > 80% (해소 실패) |
| 반응률 | 👍+👎+저장 / 발송 건수 | < 20% |

> 마지막 지표가 가장 정직합니다. **반응이 없다는 것은 큐레이션이 실패했다는 뜻**이고, 이건 프롬프트로 속일 수 없습니다.

## 4. 루프 설계 — 개념 귀속 피드백

### 4.1 v1의 끊어진 고리

```
발송 → 👍 → liked_item_ids.append(url) → (여기서 끝. 아무데도 안 쓰임)
```

### 4.2 v2의 닫힌 고리

```
① 발송        아이템 + 추출된 개념 목록을 함께 기록
② 반응        👍 / 👎 / 저장 / 무반응 / (읽음 시간)
③ 개념 귀속   반응을 아이템이 아니라 그 아이템의 개념 각각에 전파
④ 선호 갱신   개념별 선호 스코어 = f(반응 이력, 시간 감쇠)
⑤ 되먹임      다음 수집의 F축(적합도) + N축(신규성) 계산 입력
⑥ 검증        퀴즈/회상 결과 → 개념별 습득도 갱신
⑦ 재등장      습득도 낮고 선호 높은 개념 → 관련 콘텐츠 우선 서빙
```

③이 핵심입니다. `킹스레이(Ray) 분산처리 사례`에 👍를 누르면 `[분산처리, Ray, 스케줄링]` 세 개념 각각의 선호가 오릅니다. 다음날 Ray와 무관하지만 분산처리를 다루는 콘텐츠의 F축이 올라갑니다. **URL 기반으로는 절대 얻을 수 없는 일반화**입니다.

### 4.3 무반응도 신호입니다

v1은 👍/👎만 신호로 봤습니다. 실제로는 **발송된 것의 대부분이 무반응**이고, 이게 가장 큰 데이터입니다. 약한 음의 신호로 취급하되 가중치를 낮게 둡니다 (`👍 +1.0 / 저장 +1.5 / 👎 -1.0 / 무반응 -0.05`).

### 4.4 탐색-활용 균형

선호 벡터만 따르면 필터 버블에 갇힙니다. **발송 슬롯 5개 중 1개는 항상 "탐색 슬롯"**으로 고정합니다 — F축을 무시하고 N축과 D축만으로 선택합니다. 이 슬롯의 반응률을 별도 추적하면 관심 확장이 실제로 일어나는지 보입니다.

## 5. 아키텍처 v2 — 4단 퍼널

```
[수집] 58 YouTube + RSS + arXiv + HN + 뉴스레터
   │   60~90 후보/일
   ▼
[Stage 0] 기계적 게이트                                   비용 $0

   ▼
[Stage 1] 메타데이터 상대 랭킹                            Haiku 배치, ~$0.01/일
   │   제목+설명 200자만. 후보 전체를 한 프롬프트에 넣고 순위 매김

[Stage 2] 근거 확보                                       $0 (로컬 실행)
   │   yt-dlp 자막 / 본문 fetch / arXiv 초록

   │   전문(60분 영상 ≈ 12k 토큰)을 통째로 1패스 처리

   └── HTML 아카이브 + JSON 인덱스
```

### 5.1 청킹은 필요 없습니다

조사 결과 중 가장 실용적인 발견입니다. **60분 영상 ≈ 9,000단어 ≈ 12k 토큰**입니다. Anthropic 공식 가이드가 *"knowledge base가 200,000 토큰 미만이면 그냥 프롬프트에 전부 넣어라"*라고 명시하며, 12k는 그 기준의 6%입니다.

**따라서 아토믹 노트 생성 단계에서 청킹은 불필요합니다.** 나아가 자동 생성 자막에는 청킹을 **적용할 수조차 없습니다** — LangChain `SemanticChunker`는 `r"(?<=[.?!])\s+"`로 문장을 나누는데 무구두점 자막에는 `.?!`가 없어 **전체가 1개 문장이 되고 에러 없이 조용히 실패**합니다. LlamaIndex도 NLTK Punkt 기반이라 동일합니다.

> **Late Chunking과 Contextual Retrieval도 이 파이프라인에서는 불필요합니다.** 두 기법은 "청크가 문맥을 잃는다"의 해법인데, 아토믹 노트는 정의상 자립적(self-contained)으로 생성되므로 그 문제가 발생하지 않습니다. 다만 원자화가 주제 문맥을 날리는 부작용은 남으므로, **각 노트에 챕터 제목·타임스탬프를 메타데이터로 부착**해 대응합니다.

### 5.2 아토믹 노트 추출 프롬프트

Dense X Retrieval(EMNLP 2024)의 3원칙을 채택합니다. 이 정의가 제텔카스텐 아토믹 노트와 사실상 동일합니다.

1. 각 명제는 텍스트 내 **구별되는 하나의 의미 단위**에 대응한다
2. 명제는 **최소**여야 한다 — 더 쪼갤 수 없어야 한다
3. 명제는 **맥락화되고 자립적**이어야 한다 — 대명사를 실제 대상으로 치환하는 등 해석에 필요한 맥락을 모두 포함한다

3번이 구어체 트랜스크립트에서 결정적입니다. "그게", "아까 말씀드린", "이 부분이" 같은 지시어가 압도적으로 많기 때문입니다.

**프롬프트 구조는 LangChain `wfh/proposal-indexing` 방식을 따릅니다** — 규칙과 예시를 system에, 트랜스크립트를 human 메시지로 분리합니다. 원 논문 프롬프트를 그대로 쓰지 않고 이렇게 바꾼 이유가 소스 주석에 명시돼 있습니다: `# Modified from the paper to be more robust to benign prompt injection`. **외부 콘텐츠를 다루는 파이프라인에서 이 분리는 필수입니다.**

> 참고: 저자 배포 모델 `propositionizer-wiki-flan-t5-large`는 **쓰지 않습니다.** Wikipedia 전용 학습이라 구어체 성능이 미검증이고, 최신 LLM 1패스가 더 싸고 좋습니다.

### 5.4 데이터 모델 변경

```python
class EvidenceLevel(str, Enum):
    FULL = "full"           # 전체 transcript / 본문
    PARTIAL = "partial"     # 부분 / 초록
    DESCRIPTION = "description"
    TITLE_ONLY = "title_only"

class Concept(BaseModel):
    id: str                 # 정규화된 슬러그
    label: str              # 표시명
    aliases: list[str]

class Triplet(BaseModel):
    subject: str            # Concept.id
    predicate: str
    object: str

class AtomicNote(BaseModel):
    text: str               # 자립적 명제 1개
    concepts: list[str]     # Concept.id 참조
    source_timestamp: str | None
    chapter: str | None

class Scores(BaseModel):
    novelty: float          # 코드 계산
    actionability: int      # LLM
    depth: int              # LLM, evidence_level로 clamp
    half_life: str          # 닫힌 vocab
    fit: float              # 코드 계산

class ContentAnalysis(BaseModel):        # v1 대체
    evidence_level: EvidenceLevel
    scores: Scores
    domain: list[str]                    # 닫힌 vocab, 검증됨
    content_type: str                    # 닫힌 vocab
    one_line_why: str                    # "왜 중요한가" (제목 재진술 아님)
    notes: list[AtomicNote]
    triplets: list[Triplet]
    quiz: list[QuizItem]                 # evidence_level 게이트 적용
    skip_reason: str | None
```

`DigestItem`은 이제 **DB 레코드**로 저장되고 HTML은 파생물이 됩니다. 같은 날 재실행해도 이전 레코드가 살아 있습니다.

**Gmail을 거치지 않습니다.** 이유는 하나로 충분합니다 — 개인용 OAuth 앱이 verification을 받지 않으면 테스트 모드로 남고 **리프레시 토큰이 7일마다 만료**됩니다. VPS 무인 운영에서 주 1회 수동 재인증은 실격입니다. 대신 **웹 아카이브를 스크래핑**하므로 **구독조차 불필요**합니다.

**수집 경로**: Stibee는 RSS를 제공하지 않습니다(`/rss`, `/feed` 5개 전부 404 실측). 대신 `sitemap.xml`이 200으로 열리므로 → 발행호 URL 목록 → 본문 순으로 갑니다.

**파싱 시 반드시 처리할 함정 (실측 확인)**

1. **`/p/{id}` 페이지에 `<html>`이 3개 중첩**돼 있습니다. 앞의 둘은 Next.js RSC 페이로드의 이스케이프된 중복본(`>구독 취소<`)이고 **실제 본문은 3번째**입니다. 단순 grep은 중복본까지 잡습니다
2. **본문 블록은 `.stb-block-outer`** 로 잡습니다(발행호당 약 64개). 더 넓은 `.email-content`를 쓰면 노이즈가 섞입니다
3. **푸터 제거는 텍스트와 href를 둘 다 검사**해야 합니다. 퍼블리셔마다 문구가 다릅니다 — 디플릭은 Stibee 기본 푸터를 꺼서 `수신거부`가 아니라 `구독 취소`가 나옵니다. 게다가 **웹 아카이브판은 구독취소 링크의 `href`가 빈 문자열**이고(치환 전 상태) 실제 발송 메일에만 URL이 들어가므로, href 패턴만으로는 못 잡습니다
4. **신호 대 잡음이 9.5%** (113KB HTML → 10.8KB 텍스트). 추출량이 이보다 크게 많으면 푸터 제거 실패를 의심하고 로그를 남깁니다

**라이브러리**: `markdownify`(MIT). `html2text`는 **GPL-3.0**이라 배포 계획이 있으면 전염성 검토가 필요합니다. **`trafilatura`는 실패 시 `None`을 반환**해 조용한 데이터 손실이 나므로 금지, `newspaper3k`는 2018년 이후 방치라 배제. 한국어는 줄바꿈 폭 제한(기본 78)이 어절을 파괴하므로 반드시 해제합니다.

### 6.3 그 외 소스 유형

- **GitHub Trending / Releases** — 사용자가 쓰는 스택의 릴리스 노트
- **팟캐스트 RSS** — 오디오는 Whisper 로컬 처리 (Tailscale exit node 구성이면 자막과 같은 경로)
- **RSS 없는 영문 뉴스레터** (Stratechery, Import AI 등) — 여기서만 이메일 경로가 필요. 전용 주소 포워딩(Cloudflare Email Routing 등)으로 개인 Gmail과 분리

### 6.4 소스 식별자는 피드가 자기 신고하는 이름을 쓰면 안 됩니다

평가 하니스를 실측 데이터에 돌리다 발견한 결함입니다. 현재 `RawContent.source_name`은 **피드가 자기 `<title>`로 신고한 값**을 그대로 씁니다. 그 결과 소스 통계가 조용히 쪼개집니다.

| 실제 데이터에 나타난 소스명 | 건수 | 실체 |
|---|---|---|
| `kakao tech` | 43 | 카카오 기술블로그 |
| **`댓글: blog`** | **3** | **같은 카카오 기술블로그** (워드프레스 댓글 피드 제목이 유입) |
| `당근 테크 블로그 - Medium` | 9 | 당근 |
| **`당근 기술 블로그 - Medium`** | **2** | **같은 당근** (Medium 퍼블리케이션 이름 변경) |
| `NAVER D2` / `D2 Blog` | 43 / 33 | 같은 네이버 D2 |

즉 실제 소스는 6개인데 통계상 9개로 보이고, 카카오는 43이 아니라 46건입니다. **소스 도달률·통과율을 학습 신호로 쓰려는 계획(6.3절)이 이 상태로는 무너집니다.**

**수정**: 소스 정체성을 **설정에 선언한 소스 키**(YouTube는 `channel_id`, RSS는 피드 URL)로 잡습니다. 피드가 신고하는 이름은 표시용 라벨로만 쓰고, 집계·학습·프로파일 매칭은 전부 키 기준으로 합니다.

```python
class RawContent(BaseModel):
    source_key: str        # 불변. channel_id 또는 피드 URL. 집계·학습의 기준
    source_label: str      # 표시용. 상류가 바꿔도 무방
```

과거 247건은 소급 정규화 맵으로 보정합니다(`evals/` 에 매핑 테이블).

### 6.3 채널별 신뢰도 학습

소스마다 **통과율과 반응률을 누적**해서 Stage 1의 사전 확률로 씁니다. 30일간 도달률 0인 소스는 자동으로 경고합니다. v1에서 arXiv/HN이 조용히 죽어 있던 것을 다시 겪지 않기 위함입니다.

## 7. Phase 1 재정의 — 지식 회계

### 7.1 원안의 문제

> "atomic note 개수 + link 개수를 지식의 단위로 인식"

이 공식에는 정확한 선례가 있습니다. zettelkasten.de의 **Mightiness = 전체 노트 수 + 실현된 링크 수**. 하지만 후속 근거가 불리합니다.

- **가장 깊이 파본 실무자가 포기했습니다.** Will Simpson은 1,549노트/5,655링크 볼트를 전수 분석한 뒤 이 지표들이 *"성공의 나쁜 지표(poor indicators of success)"*이며 주관적 평가가 더 유용했다고 결론냈습니다.
- **Goodhart 비판이 커뮤니티 정전에 명시돼 있습니다.** zettelkasten.de(2026-02)가 직접 인용하며 왜곡 경로를 열거합니다 — 관련성 무시하고 아무거나 노트화 / 아이디어 급조 / **노트당 노력을 줄여 카운트 부풀리기**. 결론은 "산출이 아니라 투입을 측정하라"입니다.
- **교육학 실증이 불리합니다.** 개념도 메타분석(Nesbit & Adesope, 55연구·5,818명)에서 전체 효과는 g=.604로 크지만, **개인 단독 작성 g=.119(n.s.)**, **하이퍼링크 지도 g=.017(n.s.)** — 이 두 조건이 정확히 개인 Zettelkasten의 정의입니다. 개념도 채점 연구에서도 **전역 구조 점수는 채점자 신뢰도 r=.23까지 하락**하고 명제 단위 채점이 더 안정적이었으며, Novak 본인이 2판에서 가중치 합산을 버렸습니다.

### 7.2 수정안 — 평가 도구가 아니라 서술적 계기판

**단일 "지식 자산 점수"(가중합)를 만들지 않습니다.** 대신 조작 저항성이 높은 소수 지표만 시계열로 추적합니다.

| 지표 | 정의 | 조작 난이도 |
|---|---|---|
| **최대 연결요소 비율** | \|C_max\| / N | 높음 (링크 스팸으로 올리기 어려움) |
| **고아 비율** | inbound degree 0인 노트 비율 | 높음 ("수집했지만 통합 안 한 양") |
| **링크 차수 중앙값** | median(degree) — **평균 아님** | 중간 |
| **개념 지니 계수** | 링크 집중도 불평등 | 중간 |

**필수 전처리 3가지:**

1. **MOC/인덱스 노트를 별도 클래스로 분리**합니다. 이걸 안 하면 MOC 하나가 모든 지표를 흔들어 어떤 값도 신뢰할 수 없습니다.
2. **평균 대신 중앙값과 분포**를 봅니다. Will Simpson 본인이 "평균이 실제 통합 스펙트럼을 흐린다"고 지적했습니다.
3. **절대값이 아니라 자기 자신의 과거 스냅샷 대비 변화**를 봅니다. 문헌이 시사하는 최선의 설계(준거 구조 대비 유사도)는 개인 Zettelkasten에 "전문가 준거 지도"가 없어 적용 불가하므로, 시계열 자기비교가 현실적 대안입니다.

**하지 말 것:**

- ❌ **멱법칙 적합.** Broido & Clauset(*Nature Communications* 2019)이 실제 네트워크 약 1,000개 중 **강한 멱법칙 증거는 4%**, 52%는 가장 약한 증거조차 없다고 보고했고, 특히 사회 네트워크가 가장 약한 부류입니다. 로그-로그 플롯의 직선은 증거가 아닙니다. 불평등을 보려면 지니 계수로 충분합니다.
- ❌ **클러스터링 계수를 품질 지표로 쓰기.** 노트 그래프는 삼각형이 구조적으로 희소합니다 — A→B, A→C를 쓸 때 B↔C를 굳이 잇지 않기 때문입니다. 낮은 값이 품질 문제인지 표기 관습 문제인지 구분 불가합니다.
- ❌ **단어 수를 원자성 프록시로 쓰기.** 단어 수는 원자성이 아니라 장황함을 측정합니다.
- ❌ **Luhmann 90,000장을 벤치마크로 인용하기.** 실제 디지털화 실측은 73,715장이고 그마저 41%가 미전사입니다.

### 7.3 구현

**Obsidian 플러그인에 의존하지 않습니다.** 요청 지표를 모두 주는 단일 플러그인이 없고, 유일하게 중심성을 제공하는 Extended Graph조차 값을 노드 색·크기로만 소비하며 export 경로가 없습니다. **연결 요소를 주는 플러그인은 조사한 15개 중 0개**입니다.

→ **`obsidiantools` + NetworkX로 직접 계산합니다.** `vault.graph`가 NetworkX 그래프를 그대로 노출하고 `isolated_notes`로 고아를 잡습니다. 필요한 지표 전부가 수십 줄입니다. 주간 배치로 스냅샷을 DB에 적재합니다.

### 7.4 "지식의 할인율" — 착상은 옳고, 구현은 가볍게

**좋은 소식: 이 착상에는 형식적 근거가 있습니다.** 망각 곡선과 경제학의 시간 할인 함수는 **함수 형태가 실제로 일치**합니다 — 기억 모델의 retrievability 감쇠는 Loewenstein–Prelec의 일반화 쌍곡 할인(generalized hyperbolic discounting)과 동일한 꼴을 가집니다. 인적자본 이론에서도 Ben-Porath 모델이 이자율 `r`과 감가율 `δ`를 `(r+δ)`로 대칭 취급합니다. **"지식에 할인율을 적용한다"는 비유가 아니라 수학적으로 정당한 조작입니다.**

**나쁜 소식: 정밀한 모델을 만들 가치가 없습니다.**

- **FSRS-7은 35개 파라미터를 쓰는데, 파라미터 0개짜리 단순 이동평균(MOVING-AVG)에 근소하게 앞섭니다** — 로그 손실 0.3437 vs **0.3369으로 오히려 집니다.** 정교한 기억 모델에 공을 들여도 실익이 거의 없다는 뜻입니다.
- **FSRS 옵티마이저는 리뷰 512개 미만이면 최적화를 조용히 포기하고 기본 파라미터를 그대로 반환합니다.** 에러도 경고도 없어서, 사용자는 "최적화했다"고 믿지만 실제로는 기본값입니다. (`py-fsrs/fsrs/optimizer.py` — `if num_reviews < mini_batch_size: return list(DEFAULT_PARAMETERS)`, `mini_batch_size = 512`. 커뮤니티에 도는 "400~1000회"는 구전이고 확정 수치는 512입니다.)
- **"최적 유지 수준 자동 계산"은 이미 시도되고 철회된 선례가 있습니다** — Anki의 CMRR 기능이 25.07에서 제거됐습니다. 우리가 하려는 경제적 최적화와 같은 종류의 시도입니다.
- **1년 넘는 구간의 데이터가 절대적으로 부족합니다.** 유지보수자 본인이 >365일 데이터 부족을 인정하고 있는데, **하필 그 구간이 "지식 자산"에서 관심 있는 유일한 구간**입니다.
- 부수적으로, 널리 인용되는 Ebbinghaus 지수 감쇠 `e^(-t/S)`는 **원전과 다릅니다.** 원 논문은 로그 형태 `Q(t) = 1.84/((log t)^1.25 + 1.84)`입니다. 지수형으로 적은 자료를 그대로 인용하지 마십시오.

**따라서 v2의 방침:**

| 용도 | 채택 여부 |
|---|---|
| 복습 **스케줄러** (언제 다시 보여줄까) | ✅ **FSRS-6** 기성 구현 그대로 사용. 직접 튜닝하지 않음 |
| 개념별 **현재 접근가능성** 관찰 | ✅ retrievability를 그대로 기록. 해석은 나중에 |
| "지식 자산 가치" **산출** | ❌ 보류. 성과 주장을 뒷받침하는 문헌이 0건 |
| 파라미터 **자체 피팅** | ❌ 512회 게이트 + MOVING-AVG 결과를 감안하면 투자 대비 무가치 |

**버전 주의**: 최신은 FSRS-7(35 파라미터, 이중 멱함수 혼합)이지만 **아직 연구 코드이고 설치 가능한 구현체가 없습니다.** 출하 라이브러리는 전부 FSRS-6입니다(py-fsrs 6.3.1, fsrs-rs 6.6.0, ts-fsrs 5.4.1). **FSRS-6을 쓰십시오.** 덧붙여 FSRS-7에서는 *"S = R이 90%로 떨어지는 구간"*이라는 표준 정의가 깨지므로(R(S,S)가 0.83~0.95로 표류), 지표 해석은 FSRS-6 기준으로만 하십시오.

**요약하면 FSRS를 측정 도구가 아니라 스케줄러로만 씁니다.** 기성 라이브러리를 붙이고, retrievability는 로그로 쌓아두되 의사결정에 쓰지 않습니다. 1년치가 모이면 그때 "분야별 감쇠율이 실제로 다른가"를 물을 수 있고, 그게 원래 하고 싶으셨던 분석입니다. **지금 그 분석을 하려고 모델을 만드는 건 데이터가 없는 상태에서 파라미터만 늘리는 일입니다.**

### 7.5 우리 시스템의 구조적 이점 — 퀴즈가 정답 라벨을 만듭니다

FSRS를 노트 복습에 붙일 때 알려진 근본 문제가 있습니다. **일반적인 노트 리뷰에는 `Again`(실패) 라벨이 구조적으로 존재하지 않습니다.** 기준이 *"얼마나 잘 이해했는가"*라는 자기평가라서, FSRS가 학습에 쓰는 BCE 손실의 이진 타깃(`recall = 0 if rating == Again else 1`)과 맞지 않습니다. 자기평가는 관대해지기 마련이고, 그러면 모델이 배울 신호가 없습니다.

**그런데 v2는 4지선다 퀴즈를 생성합니다.** 맞았는지 틀렸는지가 **객관적 이진값**으로 나옵니다 — FSRS가 원하는 바로 그 라벨입니다. v1이 퀴즈를 넣은 건 학습 효과를 노린 것이었지만, 결과적으로 **간격반복을 제대로 붙일 수 있는 유일한 조건**을 이미 갖춰놓은 셈입니다.

→ 따라서 Sprint 3의 퀴즈 결과 기록은 **반드시 정답/오답 이진값으로** 남겨야 합니다(자기평가 4단계가 아니라). 이게 나중에 개인 파라미터 피팅이 가능해지는지를 가릅니다. 512개 게이트를 감안하면 **하루 2문항 × 260일 ≈ 1년 후** 개인화가 가능해집니다. 지금부터 쌓아야 하는 이유입니다.

> 이 영역은 선행연구가 거의 없습니다 — arXiv에서 `"Zettelkasten"` 검색 결과는 총 1건(은유로만 사용), `"Obsidian" AND "notes" AND "graph"`는 0건입니다. **확립된 방법론의 적용이 아니라 연구 공백의 개척으로 포지셔닝하는 게 정직하고, 나중에 쓸 거리도 됩니다.**

## 8. Phase 2 — 지식그래프

### 8.1 Neo4j를 지금 도입하지 마십시오

원안은 Neo4j를 지정했지만, 초기에는 과합니다. 근거:

- 개인 규모(노트 수천~수만)에서 그래프 DB의 이점이 나타나지 않습니다
- 운영 부담(서버, 백업, 스키마 마이그레이션)이 실질 가치보다 큽니다
- **7장 지표는 전부 NetworkX 인메모리로 계산 가능**합니다

**권장 진행:**

```
지금       마크다운(Obsidian 볼트) = source of truth
           + SQLite/DuckDB = 레코드·triplet·시계열
           + NetworkX = 분석 시 인메모리 그래프 구성

노드 5k+   임베디드 그래프 DB(Kùzu 등) 검토 — 프로세스 불필요
쿼리 복잡  Neo4j 승격. 이때는 정당한 선택
```

**마크다운을 source of truth로 두는 것이 핵심입니다.** DB는 언제든 재구축 가능한 파생물이어야 합니다. 그래야 Obsidian에서 직접 편집한 내용이 유실되지 않고, 그래프 백엔드를 나중에 바꿀 수 있습니다.

### 8.2 엔티티 해소가 진짜 난제입니다

triplet 추출 자체는 LLM이 잘합니다. **어려운 건 `MLOps` / `ml-ops` / `ML 운영` / `머신러닝 운영`을 같은 노드로 병합하는 것**입니다. 이게 실패하면 그래프가 동의어 파편으로 폭발하고, N축(Novelty) 계산이 무의미해집니다 — 모든 개념이 항상 "신규"로 보이기 때문입니다.

**3단 해소 파이프라인:**

```
1. 정규화       소문자화, 공백/하이픈 통일, 조사 제거
2. 후보 리콜     기존 개념과 cosine ≥ τ_recall (낮게)  → 후보군 생성
3. 판정         cosine ≥ τ_merge (높게)  → 자동 병합
                τ_recall ≤ cosine < τ_merge → LLM 판정 (배치)
                → 병합 시 alias로 등록
```

> ⚠️ **임계값을 하나로 쓰면 안 됩니다.** 이것이 초안의 오류였습니다. 실무 시스템들이 쓰는 임계값이 0.6대부터 0.9대까지 크게 갈리는데, 이는 어느 쪽이 맞아서가 아니라 **용도가 다르기 때문**입니다.
>
> - **τ_recall (후보 리콜용, 낮음)** — 놓치면 영영 병합 못 하므로 관대하게. 재현율 우선
> - **τ_merge (자동 병합용, 높음)** — 잘못 병합하면 서로 다른 개념이 한 노드로 뭉개져 되돌리기 어려우므로 보수적으로. 정밀도 우선
>
> 두 값을 구분하지 않고 남의 시스템 숫자만 가져다 쓰면 설계가 망가집니다. 회색지대(τ_recall ~ τ_merge)만 LLM에 넘기는 것이 비용·품질 양쪽에서 옳습니다.

3단계를 회색지대에서만 호출하는 게 비용 통제 지점입니다. 대부분의 개념은 1~2단계에서 결정됩니다.

**과다 병합이 과소 병합보다 위험합니다.** 과소 병합은 나중에 합칠 수 있지만, 과다 병합은 원본 구분이 소실돼 복구가 어렵습니다. 따라서 병합 이력을 **되돌릴 수 있는 형태로 로그**에 남기고(무엇을 무엇에 합쳤는지), τ_merge는 의심스러우면 올리는 쪽으로 운용합니다.

> **평가에 LLM 승률(win-rate)을 쓰지 마십시오.** LLM-as-judge의 위치 편향·길이 편향이 크다는 보고가 있어, 비교 순서를 바꾸거나 응답 길이만 달라져도 결론이 뒤집힙니다. 해소 품질은 **직접 만든 소규모 정답셋(개념 쌍 100개 수작업 라벨링)**으로 정밀도/재현율을 재는 편이 훨씬 신뢰할 만합니다. 만들기 귀찮지만 한 번 만들면 계속 씁니다.

**해소 품질은 메타루브릭의 "개념 신규율"로 감시합니다.** 이 값이 80%를 넘으면 해소가 실패하고 있다는 뜻입니다.

### 8.3 그래프를 저장소가 아니라 엔진으로

이것이 v2에서 가장 창의적인 부분입니다. KG를 "쌓아두는 곳"으로 쓰면 예쁜 그래프 뷰 말고 얻는 게 없습니다. **필터의 입력이자 아이디어 생성기로 써야 합니다.**

**(a) Novelty 엔진** — 3.2절. 추출 개념이 그래프에 있는지 조회해 N축을 코드로 계산합니다.

**(b) Serendipity 엔진 — "선제적으로 생각할 거리"의 구현**

사용자가 원하는 "선제적으로 생각할 거리, 사업 아이디어"를 일반적인 LLM 브레인스토밍으로 만들면 뻔한 결과가 나옵니다. 대신 **그래프 구조에서 후보를 뽑습니다.**

```
매주:
  1. 그래프에서 서로 멀리 떨어진(최단경로 ≥ 4) 개념 클러스터 쌍을 찾는다
  2. 그중 최근 30일 내 양쪽 모두에 새 노트가 추가된 쌍을 우선한다
  3. LLM에게: "당신은 A 영역과 B 영역을 모두 공부했습니다.
     이 둘을 잇는 구체적 가설/제품/실험을 3개 제안하십시오.
     각각 어느 노트에서 근거를 얻었는지 명시하십시오."
  4. 사용자 반응 → 개념 쌍의 "생산성" 학습
```

**이게 진짜 아이디어 생성기입니다.** LLM 혼자서는 "무엇이 당신에게 멀리 떨어진 두 영역인가"를 알 수 없지만, **당신의 그래프는 압니다.** 게다가 근거 노트를 명시하므로 환각이 아니라 실제로 읽은 것에서 나옵니다.

> 매개 중심성이 높은 노트는 종종 진짜 종합(synthesis)이 일어난 지점입니다. 이 노트들을 별도로 표시해 "당신의 사고가 교차하는 지점"으로 서빙하면 회고 도구가 됩니다.

**(c) 복습 엔진** — 습득도 낮고 선호 높은 개념의 관련 신규 콘텐츠를 우선 서빙합니다(4.2절 ⑦).

## 9. Phase 3 — hermes 통합 계약

### 9.1 현황

**hermes agent는 이 PC에 존재하지 않습니다.** `.claude/`(agents/skills/commands), Desktop, Documents를 탐색했지만 코드·README·설정 어느 것도 없습니다. 다른 머신에 있거나 아직 구상 단계로 보입니다.

→ **구현이 아니라 계약(contract)만 정의하고 열어둡니다.** 이렇게 하면 hermes의 실체가 무엇이든 붙일 수 있습니다.

### 9.2 3계층 인터페이스

**Layer 1: 파일 기반 인박스 (지금 구현)**

가장 이식성이 높고 의존성이 없습니다. 파이프라인은 항상 여기에 씁니다.

```
outbox/
  2026-07-20/
    digest.json          # 발송된 아이템 + 5축 점수 + 개념
    notes/*.md           # 아토믹 노트 (Obsidian 볼트에도 심링크)
    triplets.jsonl       # (subject, predicate, object, source_note_id)
    signals.json         # 미해결 질문, 이상 신호, serendipity 후보
    metrics.json         # 메타루브릭 지표
```

hermes가 무엇이든 이 디렉토리를 읽으면 통합됩니다.

**Layer 2: 조회 API (그래프가 커지면)**

```
GET  /concepts?q=&min_degree=       개념 검색
GET  /concepts/{id}/neighbors       이웃 탐색
GET  /notes?concept=&since=         노트 조회
GET  /bridges?min_distance=4        serendipity 후보
GET  /gaps                          습득도 낮은 개념
GET  /metrics?window=90d            지식 회계 시계열
POST /feedback                      개념 단위 반응 주입
```

**Layer 3: MCP 서버 (hermes가 LLM 에이전트라면)**

Layer 2를 MCP 도구로 감싸면 hermes가 대화 중에 당신의 지식 그래프를 직접 조회할 수 있습니다. *"내가 분산처리에 대해 뭘 아는지"*를 물으면 실제 노트를 근거로 답합니다. **이게 최종 형태로 가장 유력합니다.**

### 9.3 Push / Polling 분리

원안의 push/polling 구상을 명확히 나눕니다.

| 모드 | 트리거 | 내용 | 채널 |
|---|---|---|---|
| **Push (일간)** | 07:10 | 오늘의 5건 | Telegram |
| **Push (주간)** | 일요일 | serendipity 3건 + 지식 회계 스냅샷 | Telegram |
| **Push (조건부)** | 이벤트 | 관심 개념의 중대 변화, 메타루브릭 경보 | Telegram |
| **Pull (상시)** | 사용자 질의 | 그래프 조회, 복습, 회고 | hermes / MCP |

**조건부 push가 "선제적"의 핵심입니다.** 정해진 시각에 오는 건 선제적이 아니라 정기적입니다. *"당신이 3개월 전에 관심 가졌던 X에 중요한 후속이 나왔습니다"* 같은 것이 선제적입니다. 이건 개념별 선호 이력이 있어야만 가능하고, 4장 루프의 부산물로 자연히 얻어집니다.

## 부록 A. 검증된 YouTube 채널 58선

> 전부 `feeds/videos.xml?channel_id=` 실호출로 채널명·최신 업로드일을 확인했습니다.
> 신규 추가 시 반드시 동일 검증을 거치십시오 — 검증 없이 넣으면 엉뚱한 채널이 들어옵니다(실제 함정 5건 발견).

```bash
# @핸들 → channel_id  (사내망에서는 --ssl-no-revoke 필수)
curl -sSL --ssl-no-revoke -A "Mozilla/5.0" "https://www.youtube.com/@핸들" \
  | grep -o '"externalId":"UC[A-Za-z0-9_-]\{22\}"'

# 반드시 2차 검증 — 채널명이 기대와 일치하는지
curl -sSL --ssl-no-revoke "https://www.youtube.com/feeds/videos.xml?channel_id=UC..." \
  | grep -o '<title>[^<]*</title>' | head -3
```

> WebFetch는 이 용도로 쓸 수 없습니다 — 마크다운 변환 시 `<script>` 안의 `ytInitialData`가 통째로 날아갑니다.

*(전체 표는 `docs/sources_catalog.md`로 분리 관리)*
