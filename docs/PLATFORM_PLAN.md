# Checkpoint 플랫폼 실행 계획

> 작성 2026-09-03 · 선행 문서: `지시서.md`(제품 피치), `docs/UPGRADE_v2_DESIGN.md`(파이프라인 v2 설계)
> 이 문서는 지시서의 제품 비전을 **현 코드베이스 실측 위에서** 실행 가능한 형태로 다시 쓴 것이다.

## 0. 한 문단 요약

지시서는 "엔진은 이미 5주째 돌고 있으니 차체만 씌우면 된다"고 말한다. 실측 결과 **절반만 참**이다. 수집에서 발행까지의 배관, 계약 버저닝, CI, 관측 계층은 실제로 성숙해 있고 이것만으로 4~6주를 아낀다. 그러나 제품이 팔려는 고유 데이터(모델별 공개상태, 모델-개념-논문 엣지)는 **한 줄도 축적되지 않았다.** 5주 가동으로 쌓인 것은 한국어 일반 기술 다이제스트다.

**1차 목표는 수익이 아니라 실용성이다.** 첫 사용자는 나 자신이고, 성공 기준은 MRR이 아니라 "내가 매일 실제로 쓰는가"다. 이 전환이 로드맵 순서를 뒤집는다. 지시서가 PRO 리텐션 기능으로 마지막에 둔 **Alert가 인증도 결제도 필요 없어져 W1-2로 앞당겨지고, 2주차에 웹앱 없이 이미 쓸만한 물건이 완성된다.** 웹앱은 그 위에 얹는 열람 표면이지 실용성의 전제가 아니다.

수익화는 목표에서 빼되 문을 닫지는 않는다. **여지는 스키마와 라이선스로 남기고 코드로는 남기지 않는다**(3.4절). 그리고 착수의 1순위는 표면이 아니라 **릴리스 이벤트 데이터의 첫 1건을 오늘 적재하는 것**이다. 고유 데이터는 시간이 만드는 자산이라 착수가 늦어질수록 해자가 아니라 부채가 된다.

## 1. 확정 사항

| 결정 | 선택 | 근거 |
|---|---|---|
| 개인용 다이제스트와의 관계 | **한 파이프라인, 두 트랙** | 개인 효용을 잃지 않고 제품 실패 시 무손실 중단 가능. 지시서 W5-8의 중단 조건과 정합 |
| 산출물 언어 | **한국어 유지** | 국내에 같은 사분면 경쟁자가 없음. 단 4.4절의 수익 재산정을 전제로 함 |
| 플랫폼 범위 | **연구자 인텔리전스 4표면** | Digest 아카이브 + Tracker + Alert + Graph. 개인 학습 OS(v2 문서의 Obsidian/복습/Serendipity)는 이번 범위에서 제외 |
| 1차 목표 | **수익이 아니라 실용성** | 첫 사용자는 나 자신이다. 성공 기준은 MRR이 아니라 "내가 매일 실제로 쓰는가". 수익화는 목표에서 빼되 **스택과 라이선스 선택에서 여지만 남긴다**(3.4절) |
| 기술 스택 | **3절에서 선정** | 기준은 "1인이 주 30분으로 유지 가능한가" |

## 2. 실측 재고 조사 (2026-09-03 기준)

### 2.1 이미 있는 것 (재사용 자산)

- **파이프라인 전 구간**: `collectors.py`(RSS/YouTube/뉴스레터) → `analyzer.py`(LLM 분석) → `data/records/*.json`(구조화 레코드) → `contract.py`(발행 계약) → `docs/`(정적 산출) → `deliverers/`(Discord/Telegram)
- **발행 계약이 이미 버저닝되어 있음**: `CONTRACT_VERSION = 1`, `docs/{date}.json` + `index.json` + `latest.json`, 아카이브 베이스 `https://sangho24.github.io/ds-digest`. **이 경계가 플랫폼 설계의 핵심 접합점이 된다** (5절)
- **arXiv API 수집기가 이미 존재**: `collectors.py:300 fetch_arxiv_recent()`, `export.arxiv.org/api/query`, 카테고리 설정은 `config.py:74 arxiv_categories`
- **운영 계층**: GitHub Actions 매일 KST 07:10. 2026-07-22 ~ 09-03의 44일 중 42일 적재(결번 2일: 08-06, 08-26). `source_stats.py` 소스별 도달률 계측, `evals/` 품질 지표, 테스트 다수
- **배달 채널**: Discord/Telegram 봇이 이미 동작. Alert 표면의 발송단은 새로 만들 필요가 없다

### 2.2 비어 있는 것 (제품의 실제 재고)

| 항목 | 스키마 정의 | 실적재 |
|---|---|---|
| `triplets` (그래프 엣지) | `models.py`에 있음 | **0 / 179** |
| `notes` (아토믹 노트) | 있음 | **0 / 179** |
| `scores` (5축 루브릭 N/A/D/H/F) | 있음 | **0 / 179**, 여전히 단일 `relevance_score` |
| `concepts` | 가동 중 | 44노드. **엣지 없음**, 한국어 자유텍스트("AI 비용 효율성"), 모델·논문과 미연결 |
| 모델 릴리스 상태 | **없음** | 0 |

즉 지시서 V2의 "41노드 그래프"는 프로토타입 세션에서 즉석 추출한 것이고, **파이프라인이 지속 생산하는 자산이 아니다.**

**그래프와 추천 로직은 코드 수준에서 전부 부재하다.** 필드 선언만 있고 구현 사이가 통째로 비어 있어, 스키마만 보면 곧 동작할 것처럼 보이는 것이 함정이다.

| 단계 | 실태 |
|---|---|
| triplet 추출 | **없음.** `analyzer.py` 프롬프트가 triplet을 요구하지 않는다. 이것이 0/179의 직접 원인 |
| triplet 정규화·엔티티 해소 | 없음 |
| 계약 노출 | **오히려 명시적으로 제외 중.** `contract.py:60` "내부값(scores/notes/triplets)은 뺀다" |
| 엣지 저장 | 없음 |
| PPR 계산 | 없음. `networkx`·`scipy` 등 그래프 라이브러리가 `requirements.txt`에 없다 |
| UI | 유실. `checkpoint-graph-prototype.html`이 저장소에 없다(세션 산출물) |

`triplets`는 `models.py:193`에 타입 선언만 존재한다. **따라서 W6-9는 "프로토타입 재구현"이 아니라 6단계 전부를 처음 만드는 작업이다.** 계약 확장도 함께 필요하다.

### 2.3 소스 구성이 제품과 다른 물건이다

수집 실적(179건):

```
rss/HackerNews            54    youtube/Two Minute Papers   22
youtube/MLST              13    rss/토스 기술블로그          11
youtube/3Blue1Brown        9    newsletter/디플릭             8
newsletter/트렌드라이트     7    youtube/Yannic Kilcher        7
rss/D2, 당근, Netflix, Airbnb, Spotify ...
rss/arXiv:cs.*             7    (6개 카테고리 합계)
```

`content_type = release`로 분류된 20건을 전수 확인한 결과 13건이 `Show HN` / `Launch HN`이고, 나머지 7건도 vLLM·WebLLM·Petals 같은 OSS 추론 도구이거나 무관한 기사다. **프런티어 모델 릴리스는 0건이다.** 모델명도 구조화 필드가 아니라 본문 텍스트에만 있어, 정규식 추출 시 "Claude Shannon", "Claude or"가 함께 걸린다(176종 후보 중 다수가 오탐).

**결론: Tracker의 현재 재고는 0이고, 이건 차체가 아니라 연료를 바꾸는 일이다.**

## 3. 기술 스택 선정

선정 기준은 성능도 유행도 아니고 **1인 유지보수 가능성** 하나다. 부품 수를 줄이고, 경계를 적게 만들고, 장애 시 복구 경로가 짧은 쪽을 고른다.

### 3.1 가장 중요한 결정: Python 파이프라인을 재작성하지 않는다

TypeScript로 통일하고 싶은 유혹이 있지만 **하지 않는다.** 13.7k LOC에 테스트와 evals가 붙어 있고 5주 실운영으로 검증됐다. 재작성은 이 검증을 전부 버리는 일이다. 언어 이원화 비용은 실재하지만, 그 비용은 **경계를 하나로 좁히면** 관리 가능하다. 마침 `contract.py`가 이미 그 경계다.

### 3.2 선정 결과

| 층 | 선택 | 대안 대비 근거 |
|---|---|---|
| 수집·분석 워커 | **Python 유지** (현 코드) | 3.1절 |
| 워커 실행 | **GitHub Actions 유지**, 실패 알림 추가 | 이미 동작. VPS는 부품과 비용이 늘 뿐 |
| 워커↔플랫폼 경계 | **버저닝된 JSON 아티팩트** (`contract.py` 확장) | 워커가 DB 스키마를 몰라도 됨. 스키마 지식이 한 곳에만 존재 |
| DB | **Postgres (Neon)** | 워치리스트·알림·구독·그래프 엣지는 관계형이 필요. 파일 기반은 4표면을 못 버팀. 서버리스라 유휴 비용 0 |
| 적재(ingest) | **TS 단일 진입점 스크립트** | Python이 DB를 직접 쓰면 스키마 드리프트가 최대 유지보수 리스크가 됨. 쓰기 경로를 하나로 |
| ORM/마이그레이션 | **Drizzle ORM** | 스키마가 곧 TS 타입. SQL에 가깝고 마이그레이션이 파일로 남아 추적 가능. Prisma 대비 런타임 부품이 적음 |
| 앱 | **Next.js 15 (App Router) + React 19 + TypeScript** | 선호 스택. 서버 컴포넌트로 DB 조회를 서버에 두면 API 층 자체가 불필요 |
| UI | **Tailwind + shadcn/ui** | 선호 스택. 컴포넌트가 코드로 복사되어 들어와 의존성 잠김이 없음 |
| 상태 | **URL 쿼리스트링 우선, 필요 시 Zustand** | Tracker/Graph의 필터 상태는 URL에 두면 공유 가능한 링크가 공짜로 생김. 전역 스토어는 최소화 |
| 폼 | **React Hook Form + Zod** | 선호 스택. Zod 스키마를 워커 계약 검증에도 재사용 |
| 인증 | **당장 넣지 않음.** 자리만 비워둠 | 단일 사용자에게는 불필요. 필요해지면 Auth.js(GitHub OAuth). 3.4(c) |
| 호스팅 | **Vercel** | Next.js 1급 지원, 무료 티어, 프리뷰 배포 |
| 인용 그래프 원천 | **OpenAlex (CC0) 1순위** | 라이선스가 깨끗해 재배포·상용 여지에 제약이 없다. 3.4(b) |
| 그래프 계산 | **Postgres 엣지 테이블 + 클라이언트 PPR** | 노드 수천 규모에서 그래프 DB는 과함(v2 문서 8.1절과 동일 결론). 프로토타입에서 브라우저 PPR이 이미 검증됨 |
| 알림 발송 | **기존 Discord/Telegram `deliverers/` 재사용**, 이메일은 Resend | 발송단을 새로 만들지 않음 |
| 결제 | **고려하지 않음** | 코드 구조에 영향이 없어 나중에 얹으면 된다. 3.4(c) |

### 3.3 명시적으로 채택하지 않는 것

| 항목 | 사유 |
|---|---|
| Python 파이프라인의 TS 재작성 | 검증된 자산 폐기. 3.1절 |
| Python에서 DB 직접 쓰기 | 스키마 드리프트. 쓰기 경로를 TS 한 곳으로 |
| 그래프 DB (Neo4j/Kùzu) | 개인~소규모에서 이점 없음. v2 문서에서 이미 폐기 판정 |
| Supabase 풀스택 | DB+Auth+Storage 묶음은 편하지만 종속이 크다. Neon(DB) + Auth.js로 부품을 갈아끼울 수 있게 둔다 |
| 별도 REST/GraphQL API 층 | 서버 컴포넌트로 충분. 외부 API 공개는 v2 과제 |
| 마이크로서비스·컨테이너 오케스트레이션 | 1인 운영에 순손실 |

### 3.4 수익화 여지를 남기는 방법 (지금 구현하지는 않는다)

수익화는 1차 목표에서 뺐다. 그러나 **나중에 닫히는 문과 열려 있는 문을 구분해 두어야** 한다. 원칙은 하나다. **여지는 스키마와 라이선스로 남기고, 코드로는 남기지 않는다.** 인증·결제·멀티테넌시를 미리 구현하는 것은 순수한 낭비다.

#### (a) 코드 라이선스: 지금 상태가 최선이다

저장소에 `LICENSE` 파일이 **없다.** 이 상태의 법적 의미는 "모든 권리 유보"이고, 남이 쓸 수 없는 대신 **내가 나중에 무엇으로든 열 수 있다.** 단독 저작자이므로 AGPL로 열든, BUSL로 열든, 상용 라이선스를 따로 팔든 자유롭다. 반대 방향(공개했다가 회수)은 불가능하다. **따라서 지금 라이선스를 붙이지 않는 것이 옵션을 가장 많이 보존한다.**

> **가장 흔한 함정: 외부 기여(PR)를 라이선스 합의 없이 병합하는 것.** 기여자가 한 명이라도 생기는 순간 단독 재라이선스 권한이 사라지고, 나중에 유료화하려면 전원의 동의를 받아야 한다. 공개 후 PR을 받을 생각이라면 그 시점에 CLA를 먼저 준비한다.

#### (b) 데이터 라이선스: 여기가 실제 제약이다

코드보다 데이터 쪽이 까다롭다. 다행히 **현 계약 산출물이 이미 안전한 구조다.** `docs/*.json`은 원문 본문을 내보내지 않고 `summary`(평균 28자, 최대 44자) · `key_points` · `tags` 같은 자체 생성물만 담는다. **이 규율을 릴리스 트랙에도 그대로 적용한다.**

| 원천 | 라이선스 성격 | 취급 규칙 |
|---|---|---|
| HF Hub 메타데이터 (생성일·수정일·라이선스명·커밋시각) | 사실 데이터 | 자유롭게 저장·재배포 |
| 모델 카드 본문 | 각 리포의 라이선스를 따름 | **링크 + 자체 요약만.** 전문 저장·재배포 금지 |
| arXiv | 메타데이터 활용은 허용, 전문 미러링은 제한 | **초록 전문을 저장하지 않는다.** 링크 + 자체 요약 |
| **OpenAlex** | **CC0** | 제약 없음 |
| Semantic Scholar | 이용약관에 조건이 붙을 수 있음 | 상용 여지를 남기려면 후순위 |
| 뉴스레터·기업 기술블로그 | 저작권 있는 콘텐츠 | **개인 digest 트랙 전용. 공개 표면에 본문 노출 금지** |

**이것이 W6-9의 실제 설계 결정을 하나 바꾼다: 인용 그래프는 OpenAlex(CC0)를 1순위로 쓴다.** 지시서는 "Semantic Scholar·OpenAlex 무료"라고 둘을 동급으로 적었지만, 상용화 여지를 남기려면 동급이 아니다.

그리고 **두 트랙 분리는 편의가 아니라 법적 필요이기도 하다.** 저작권 있는 뉴스레터 본문이 개인 트랙에만 머무르고 공개 표면으로 새지 않는 경계가 있어야 한다.

#### (c) 스택에서 미리 남겨둘 것 (비용이 거의 0인 것만)

- **DB 스키마에 `user_id`를 처음부터 넣는다.** 단일 사용자로 운영하되 컬럼은 존재한다. 나중에 멀티테넌시로 갈 때 데이터 이관이 필요 없어진다. 지금 드는 비용은 컬럼 하나다
- **라우트를 인증 전제로 구성한다.** Auth.js 미들웨어가 들어갈 자리만 비워두고 실제 인증은 넣지 않는다
- **Vercel Hobby 티어는 상업적 이용을 금지한다.** 수익이 발생하는 순간 Pro($20/mo)가 필요하다. Neon·Resend 무료 티어도 마찬가지다. 전환 비용이 예측 가능하다는 것만 알고 있으면 되고, 지금 대비할 것은 없다
- 결제(Lemon Squeezy 등)는 코드 구조에 영향을 주지 않으므로 **전혀 고려하지 않는다**

### 3.5 저장소 구조

기존 저장소를 모노레포로 확장한다(새 저장소를 파지 않는다. git 이력과 CI가 이미 여기 있다).

```
ds-digest/
  app/                  # Python 워커 (기존, 유지)
  data/                 # 워커 산출 + 워치리스트 (기존)
    watchlist.yaml      # (작성됨) 추적 대상 조직, 사람이 관리
    releases.jsonl      # (신규) 상태 전이 이벤트 로그, append-only
  docs/                 # 정적 산출 + 설계 문서 (기존, 계약 산출 유지)
  web/                  # (신규) Next.js 앱
    src/db/schema.ts    # Drizzle 스키마 = 단일 소스
    src/ingest/         # 계약 JSON -> Postgres 적재 진입점
```

## 4. 아키텍처

### 4.1 데이터 흐름

```
[수집] RSS/YouTube/뉴스레터/arXiv  +  (신규) 공식 블로그 / HF Hub API
                    |
[분석] analyzer.py  ->  두 트랙으로 분기
                    |                        |
          (개인) digest 트랙        (제품) release 트랙
                    |                        |
[레코드] data/records/*.json        data/releases.jsonl
                    |                        |
[계약] contract.py  ->  docs/{date}.json, index.json, latest.json, (신규) tracker.json
                    |
[적재] web/src/ingest  ->  Postgres (Neon)
                    |
[표면] Next.js: Digest 아카이브 / Tracker 보드 / Graph 탐색 / Alert 설정
                    |
[발송] deliverers/ (Discord·Telegram) + Resend(이메일)
```

**경계는 딱 하나다: 버저닝된 계약 JSON.** 워커는 Postgres를 모르고, 웹앱은 수집기를 모른다. 한쪽이 죽어도 다른 쪽이 마지막 계약 산출로 계속 동작한다.

### 4.2 Tracker 상태 머신 (제품의 심장)

지시서의 "발표 → 리포트 → 가중치 → 라이선스"를 모델당 상태로 정의한다.

```
announced_at    마케팅 블로그/공식 발표
report_at       기술 리포트 또는 논문 URL
weights_at      가중치 공개 (HF 리포지토리)
model_card_at   실체 있는 모델 카드
license         Apache-2.0 / 커스텀 / 미공개
```

각 전이는 **증거를 달고** append-only 로그에 기록한다.

```
{ model_id, transition, observed_at, source_url, method, confidence }
```

- `method`: `hf_api` | `official_rss` | `arxiv` | `manual`
- `confidence`: `verified`(1차 출처 응답으로 확인) | `unverified`(LLM 추정)
- **UI에서 `unverified`는 [미확인] 라벨로 표시한다.** 지시서의 신뢰 규율을 데이터 모델 수준에서 강제하는 장치다.

### 4.3 엔티티 해소를 정면으로 풀지 않는다

v2 문서 8.2절이 "엔티티 해소가 진짜 난제"라고 정확히 지적했고, 2.3절 실측이 이를 재확인했다(정규식 176종 중 다수 오탐). **닫힌 워치리스트로 회피한다.**

**모델이 아니라 조직 단위로 감시한다.** 특정 버전(`Qwen3.8-Max`)을 하드코딩하면 다음 버전이 나올 때마다 수동 등록이 필요하다. `조직 + 시리즈 접두사`로 감시하면 신규 버전이 자동 포착되고 사람은 조직만 관리한다.

- `data/watchlist.yaml`에 조직을 등록: `hf_org`, `series`(prefix), 공식 블로그 피드, `kind`
- 매칭은 **HF org 소속 + series prefix 정확 매칭**만 사용한다 (LLM 아님)
- LLM의 역할은 "여기 없는 신규 조직·시리즈 후보 제안"으로 한정하고, `candidates:`에 쌓아 주간 검수에서 사람이 승인한다

이렇게 하면 "Claude Shannon" 오탐이 구조적으로 불가능해진다. 초안은 **조직 16개**(가중치 공개형 12, 폐쇄형 4)이며 전부 `verify` 표시가 붙어 있다. HF org 이름의 실재 여부는 추정이므로 W0 프로브 전까지 신뢰하지 않는다.

**두 종류를 나눠 추적한다.**

- `weights-open`: 4단계 전이가 모두 관측된다. 자동화 가치가 가장 크다
- `closed`(Anthropic·OpenAI·Gemini): 가중치 전이가 없어 `announced_at` / `report_at` 두 단계만 추적한다. 그래도 가치가 있다. **지시서의 문제의식("출시일엔 마케팅 블로그뿐, 알맹이는 리포트 공개일에 나온다")이 가장 선명하게 드러나는 쪽이 여기다**

**국내 조직(LG AI EXAONE, Upstage Solar)을 포함시켰다.** 영어권 트래커가 다루지 않는 영역이고, 한국어 서비스의 실제 차별점이 된다.

### 4.4 무엇을 "쓸만하다"고 할 것인가

수익을 목표에서 뺐으므로 성공 지표를 다시 정의한다. **첫 사용자는 나 자신이고, 이탈하지 않는 유일한 사용자다.**

| 표면 | 실용 가치의 형태 | 매일 쓰이는가 |
|---|---|---|
| **Alert** | "GLM 가중치 떴나?"를 찾아보지 않아도 알게 됨 | **가장 높다.** 능동적으로 열 필요가 없는 유일한 표면 |
| **Digest 아카이브** | "2주 전 그 글 뭐였지"를 찾을 수 있음 | 높다. 현재 42일치가 쌓였는데 검색이 불가능하다 |
| **Tracker** | 특정 모델의 공개 상태를 한 화면에서 확인 | 중간. 릴리스는 주 1~2건이라 매일 볼 이유는 약하다 |
| **Graph** | 읽을 논문을 고름 | 낮다(초기). 데이터가 쌓여야 작동하는 콜드스타트 구조 |

**이 표가 로드맵 순서를 뒤집는다.** 지시서는 Alert를 PRO 리텐션 기능으로 보고 마지막에 두었지만, 수익화를 빼면 **Alert는 인증도 결제도 필요 없다.** 내 Discord/Telegram 채널로만 쏘면 되고 배달단(`deliverers/`)은 이미 동작한다. 따라서 **Alert를 W1-2로 당긴다.**

그 결과 **2주차에 이미 쓸만한 물건이 완성된다.** 웹앱 없이도 "릴리스 감시 + 알림"이 돌기 때문이다. 웹앱은 그 위에 얹는 열람 표면이지, 실용성의 전제가 아니다.

### 4.5 실용 지표

다음 세 가지만 센다. 전부 자동 계측이 가능하다.

1. **알림 유용률**: 발송한 알림 중 내가 실제로 링크를 연 비율. 낮으면 워치리스트나 전이 정의가 잘못된 것이다
2. **아카이브 조회**: 주당 검색 횟수. 0이면 아카이브 표면은 만들 가치가 없었다는 뜻이다
3. **데이터 커버리지**: 워치리스트 모델 중 4단계 상태가 모두 채워진 비율. 이것이 곧 자산의 두께다

## 5. 데이터 모델

Drizzle 스키마(`web/src/db/schema.ts`)가 단일 소스다. 아래는 핵심 테이블의 의도이며 컬럼은 구현 시 확정한다.

| 테이블 | 역할 | 비고 |
|---|---|---|
| `models` | 추적 대상 모델 | `watchlist.yaml`에서 동기화. canonical name, org, aliases |
| `release_events` | 상태 전이 로그 | **append-only.** 4.2절 구조. 같은 전이의 재관측은 새 행으로 쌓고 최신만 표시 |
| `items` | Digest 아이템 | `docs/{date}.json` 계약에서 적재. 아카이브·검색의 원천 |
| `concepts` | 개념 노드 | 기존 `data/concepts.json` 이관 + 릴리스 트랙에서 신규 유입 |
| `papers` | 논문 노드 | arXiv id를 자연키로. 초록·저자는 arXiv API에서 |
| `edges` | 그래프 엣지 | `(src_type, src_id, dst_type, dst_id, relation, weight, evidence_url)` |
| `users` / `watchlists` / `alert_prefs` | Alert 표면 | Auth.js 세션과 연결 |

### 5.1 엣지가 생기는 경로

지금 `triplets`가 0인 이유는 스키마가 없어서가 아니라 **엣지를 만들 계기가 없어서**다. 릴리스 트랙이 그 계기를 만든다.

```
모델 --uses_technique--> 개념      (기술 리포트 분석에서)
모델 --described_in--->  논문      (리포트/arXiv 링크에서, 링크가 곧 증거)
논문 --about----------> 개념      (초록 분석에서)
논문 --cites---------->  논문      (Semantic Scholar / OpenAlex API, 둘 다 무료)
```

**`model --described_in--> paper` 엣지가 후발주자가 복제하기 어려운 자산이다.** 인용 그래프는 누구나 API로 가져오지만, "이 모델의 기술 리포트가 저 논문이다"는 큐레이션의 산물이다. 현재 레코드에 arXiv abs 링크를 포함한 아이템이 29건 있어 초기 시드로 쓸 수 있다.

## 6. 로드맵

수익화를 뺀 결과 순서가 바뀌었다. **쓸만해지는 시점을 최대한 앞으로 당긴다.** 각 단계는 측정 가능한 검증 기준을 갖고, 미달 시 다음으로 가지 않는다.

### W0 - 성립 판정 (2일, 코드 거의 없음)

제품이 성립하는지를 먼저 잰다. 이 단계를 건너뛰면 나머지가 헛일이 될 수 있다.

- [ ] **네트워크 프로브를 로컬 셸에서 실행.** 이번 세션의 샌드박스에서는 HuggingFace API 호출이 `Connection reset by peer`로 전부 차단됐다. **API 자체의 문제인지 환경 제약인지 미확인 상태다.** 회사망(PwC 프록시) 여부도 함께 확인할 것
  - `https://huggingface.co/api/models?author=Qwen&sort=lastModified&limit=3`
  - 워치리스트 조직의 공식 블로그 피드 응답
- [ ] **워치리스트 확정** (`data/watchlist.yaml` 초안 작성 완료, 조직 16개). `verify` 표시된 HF org 이름과 블로그 피드의 실재 여부를 프로브로 검증하고 틀린 것을 고친다
- [ ] **지난 90일 소급 재구성**: HF API의 `createdAt` / `lastModified` / `/api/models/{id}/commits/main`으로 각 모델의 가중치·모델카드 공개 시점을 역산
- [ ] **판정 수치 산출**: 지난 90일간 관측 가능한 상태 전이 건수

> **검증 기준: 90일 소급에서 상태 전이 20건 이상**(우선순위 1~2 조직 기준). 미달이면 릴리스 밀도가 알림을 지탱하지 못한다는 뜻이므로 7절 중단 절차로 간다.
>
> 부수 효과가 크다. 성공하면 **첫날에 90일치 고유 데이터가 생긴다.** 지시서 W1-2의 "5주치 브리핑 소급 파싱"보다 값진 소급이다.

### W1-2 - 릴리스 파이프라인 + Alert (여기서 이미 쓸만해진다)

- [ ] `app/collectors_release.py`: 공식 블로그 RSS + HF Hub API 수집기
- [ ] `app/releases.py`: 워치리스트 매칭(정확 매칭만) + 상태 전이 판정 + `releases.jsonl` append
- [ ] **Alert 발송**: 상태 전이 발생 시 기존 `deliverers/`로 Discord/Telegram 발송. **인증·DB·웹앱 없이 동작한다**
- [ ] `contract.py` 확장: `CONTRACT_VERSION = 2`, `docs/tracker.json` 발행 추가 (v1 소비자를 깨지 않도록 기존 필드 유지)
- [ ] `docs/tracker.html`: 정적 보드. **GitHub Pages가 이미 서빙 중이므로 배포 작업 없이 URL이 생긴다**
- [ ] 워커 실패 알림 + `concurrency` 가드. **결번 2일의 원인을 먼저 규명한다** - push 경합이면 이 가드로 해소된다

> **검증 기준: (1) 상태 전이 알림이 실제로 내 채널에 도착한다. (2) 2주간 오탐 0건**(수동 전수 검수). 오탐이 나오면 매칭 규칙을 좁힌다.
>
> **이 시점에서 웹앱 없이도 제품의 핵심 효용이 완성된다.** 이후 단계는 전부 "열람 편의"의 개선이다.

### W3-5 - 웹앱 골격 + 아카이브 검색

실용 순위 2위(4.4절)를 구현한다. 42일치가 쌓였는데 검색이 안 되는 상태를 해소한다.

- [ ] `web/` Next.js 15 앱 초기화, Vercel 연결, Neon 프로젝트 생성
- [ ] `web/src/db/schema.ts` + Drizzle 마이그레이션 (5절). **`user_id`를 처음부터 넣되 단일 사용자로 운영**(3.4절)
- [ ] `web/src/ingest`: 계약 JSON을 읽어 Postgres에 적재하는 단일 진입점. GitHub Actions에서 워커 직후 실행
- [ ] 표면 2개: **Digest 아카이브**(검색·필터, 상태는 URL 쿼리스트링) / **Tracker 보드**(정적판을 DB 기반으로)

> **검증 기준: (1) 계약 JSON과 DB 조회 결과가 같은 날짜에 같은 내용을 보인다(대조 스크립트 통과). (2) 2주간 아카이브 검색을 내가 5회 이상 실제로 쓴다.** 두 번째가 미달이면 아카이브 표면은 과잉이었다는 뜻이므로 Graph로 넘어가지 말고 재검토한다.

### W6-9 - Graph 표면 (재사용 자산 0)

**2.2절에서 확인했듯 이 단계는 재구현이 아니라 6단계 전부를 처음 만드는 작업이다.** 앞 단계들과 달리 재사용할 자산이 없으므로 기간을 넉넉히 잡았다.

- [ ] `analyzer.py` 프롬프트에 **triplet 추출을 추가**한다. 지금은 요구 자체가 없어서 0/179다. **릴리스 트랙 한정으로** 시작하고 개인 digest 트랙까지 한 번에 켜지 않는다. 범위를 좁혀야 엔티티 해소가 관리 가능하다
- [ ] triplet 정규화: 개념 슬러그화 + 기존 `data/concepts.json`(44노드)과의 병합
- [ ] **`contract.py`의 제외 규칙을 바꾼다.** 현재 `_item_to_contract()`가 `triplets`를 계약에서 명시적으로 빼고 있다. 그래프를 표면에 올리려면 이 결정을 뒤집어야 한다
- [ ] 엣지 저장: Postgres `edges` 테이블 (5절)
- [ ] **OpenAlex**로 `paper --cites--> paper` 보강 (CC0. Semantic Scholar는 이용약관 조건 때문에 후순위, 3.4(b))
- [ ] PPR 계산: 노드 수천 규모이므로 클라이언트 계산으로 충분하다. 서버 측 그래프 라이브러리 의존을 추가하지 않는다
- [ ] Graph 표면: 관심 모델 3개 선택(PPR 시드) → 추천 랭킹 → 설명 카드 → 최단경로 기반 "왜 추천됐나"

> **검증 기준: `model --described_in--> paper` 엣지 30개 이상, 그중 90% 이상이 `verified`. 그리고 추천 상위 10건 중 내가 실제로 읽은 논문이 1건 이상.** 후자가 진짜 기준이다. 엣지 수는 작동의 증거일 뿐 유용함의 증거가 아니다.

### W10+ - 공개 여부 판단 (선택)

여기까지가 "실용적으로 쓸만한 것"의 범위다. 그 이후는 별도 결정 사항으로 남긴다.

- 공개할지, 개인 도구로 둘지
- 공개한다면 이메일 구독(Resend) 또는 링크 공유만
- 유료화는 이 단계에서 처음 검토한다. 3.4절이 그때까지의 선택지를 열어둔다

## 7. 중단 기준

착수보다 중요한 것이 중단 조건을 미리 못 박는 일이다. 수익 목표가 없으므로 기준도 **"내가 쓰는가"** 하나로 통일된다.

| 시점 | 중단 조건 | 회귀 경로 |
|---|---|---|
| W0 | 90일 소급 상태 전이 20건 미만 | 자동 추적 폐기. 개인 Digest에 릴리스 요약만 추가 |
| W2 | 오탐이 매칭 규칙 수정으로 잡히지 않음 | 자동 판정 폐기, 수동 큐레이션 보드로 축소 |
| W2 | 알림이 오는데 **내가 링크를 열지 않는다** | 워치리스트 또는 전이 정의가 틀린 것이다. 축소가 아니라 재설계 |
| W5 | 2주간 아카이브 검색 5회 미만 | 아카이브 표면 동결. Graph로 넘어가지 않고 W1-2 결과물만 유지 |
| W9 | 추천 상위 10건 중 실제로 읽은 논문 0건 | Graph 폐기. Tracker + Alert만 남긴다 |

각 중단 지점에서 **이미 만든 것은 계속 쓸 수 있다.** W2까지만 가도 "릴리스 감시 + 알림"이 남고, 이것만으로 착수 목적을 달성한다. 이것이 "한 파이프라인 두 트랙"과 "Alert 우선"을 고른 이유다.

**가장 중요한 중단 규율:** 위 조건에 걸렸을 때 "조금만 더 고치면 될 것 같다"는 판단으로 넘어가지 않는다. v2 문서 1.1절이 기록한 실패 패턴이 정확히 그것이었다. 프롬프트를 고치면 될 것 같아서 4개월간 계속 고쳤고, 실측해 보니 하나도 고쳐지지 않았다.
