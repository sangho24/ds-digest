RankServe: Rank-Aware CPU-GPU Scheduling for Memory-Constrained MoE Serving

GPU 메모리 제한 MoE 서빙 가속

배경과 위치
MoE 모델은 메모리 요구량이 커서 기존 서빙 방식은 전문가 인기만 고려해 GPU에 적재했다. RankServe는 전문가 랭크와 토큰 로드를 포함한 비용 절감량을 기준으로 CPU‑GPU 스케줄링을 수행해, 메모리 제약 하에서 효율적인 서빙을 목표로 하는 모델 서빙 연구 흐름에 새로운 접근을 제시한다.
실행가능성 6
깊이 6
  • · RankServe는 전문가의 랭크와 토큰 부하를 기반으로 GPU 상주 여부를 바이트당 절감량으로 평가해 우선순위를 정한다.
  • · 가변 랭크 런타임을 도입해 공통 랭크 패딩 없이 이질적인 전문가들을 그룹화된 행렬 곱셈으로 실행한다.
  • · 단일 CPU‑GPU 플랫폼에서 TTFT 1.69‑2.29배, TPOT 1.71‑2.48배 속도 향상을 달성했다.
Action Items
  • CPU‑GPU 스케줄링 로직을 변형해 혼합 정밀도 Transformer 레이어를 메모리 사용량에 따라 동적으로 배치하면, 메모리 제한 환경에서 추론 속도를 높일 수 있다.
  • 엣지 디바이스에서 대규모 모델의 일부 모듈을 가변 랭크 실행으로 처리해, 제한된 온칩 메모리와 외부 메모리 간 전송 비용을 최소화한다.
  • 데이터 파이프라인에서 대용량 피처 집합을 랭크 기반으로 SSD와 RAM 사이에 캐시하고, 사용 빈도와 크기에 따라 저장 위치를 최적화한다.

파드는 떴는데 왜 통신이 안 될까? kube-proxy nftables 전환 여정

kube-proxy 규칙 지연이 서비스 가용성을 위협한다

실행가능성 7
깊이 7
  • · kube-proxy 규칙 동기화 지연이 서비스 가용성을 저해하고, 노드 스케일아웃 시 문제를 악화시킨다
  • · iptables 모드에서는 Service·Endpoint 규칙을 순차 비교해 O(N) 비용이 발생하고, 전체 동기화에 4분 이상 걸릴 수 있다
  • · nftables 모드로 전환하면 map 기반 O(1) 조회와 변경량 기반 증분 업데이트로 지연이 크게 감소한다
Action Items
  • nftables와 동일한 map 기반 라우팅을 API 게이트웨이의 요청 매핑에 적용하면 라우팅 지연을 크게 낮출 수 있다
  • kube-proxy의 증분 동기화 방식을 구성 관리 시스템에 도입하면 전체 설정 재로드 없이 변경된 부분만 적용해 서비스 중단을 최소화한다
  • 규칙 동기화 지연 모니터링을 활용해 자동 스케일링 시점에 사전 워밍업을 트리거하면 신규 Pod의 초기 통신 실패를 방지한다
퀴즈 1문항
iptables 모드에서 kube-proxy 규칙 조회 비용이 O(N)인 이유는 무엇인가?
① 규칙이 트리 구조로 저장돼서
② Service와 Endpoint 규칙을 순차적으로 비교하기 때문
③ 해시 맵을 사용하지 않기 때문
④ 커널이 규칙을 캐시하지 않기 때문
② Service와 Endpoint 규칙을 순차적으로 비교하기 때문
iptables 모드에서는 Service마다, Endpoint마다 개별 규칙을 만들고 패킷이 들어오면 Service 규칙을 위에서부터 순차 비교한 뒤, 해당 Service의 Endpoint 규칙을 다시 순차 비교해 목적지를 찾는다. 이 두 단계의 순차 탐색이 O(N) 비용을 초래한다.
